# Dynamic SCD Framework

A reusable Talend pattern for metadata-driven SCD Type 2 historisation of source-system tables. One control/dispatcher/worker stack handles **many tables**, parametrized by a meta table that lists which tables to process and what their business-keys are. Seen across multiple cimt projects. This file documents the pattern so it can be recognized and audited in any project that uses it.

## How to detect this pattern in a project

Scan in this order:

1. **A meta-table named `<schema>.*_META_TABLE_OBJECTS`** (or similar — sometimes `meta.dyn_import_config`). Columns typically include: `db_staging_table`, `db_scd_table`, `db_scd_view`, `columns_to_import`, `columns_business_keys`, `paging_size_import`, plus activation flags like `inactive` and `SCD_process`.
2. **A trio of job names** along the lines of `*_dyn_imp_staging_control` + `*_dyn_imp_staging_worker` and `*_dyn_imp_scd_control` + `*_dyn_imp_scd_dispatcher` + `*_dyn_imp_scd_worker_data` + `*_dyn_imp_scd_worker_ddl`. Control loops via `tFlowToIterate` over the meta table; the dispatcher loops via `tFlowToIterate` over `META_BATCH_ID`.
3. **Routine-based MD5 helper** in `code/routines/*.java` such as `generateMDG5SQL(hashType, columns)` that returns a `CONVERT(VARCHAR(32), HASHBYTES('MD5', concat(...)), 2)` SQL fragment. Aufrufer in `tDBInput`-`QUERY`-Attributen.
4. **Standardized meta-columns on every staging and SCD table**: `META_BATCH_ID`, `META_LOAD_DATETIME`, `META_HK`, `META_HV`, `META_DELETION_DATETIME`.
5. **`_current` views per SCD table**, generated by the `*_scd_worker_ddl` job, using `LEAD()` window function to keep only the latest row per HK.

If you see (1) + (2), the project uses this framework. (3)–(5) confirm the mechanics.

## Architecture

```
┌────────────────────────────────────────────────────────────────────┐
│  meta.<x>_META_TABLE_OBJECTS                                       │
│  (one row per source table to be processed)                        │
└─────────────────────────────────┬──────────────────────────────────┘
                                  │ control loops via tFlowToIterate
                                  ▼
                  ┌──────────────────────────────────┐
                  │  *_dyn_imp_staging_control       │
                  │  reads meta, iterates tables     │
                  └────────────────┬─────────────────┘
                                   │ tRunJob per table
                                   ▼
                  ┌──────────────────────────────────┐
                  │  *_dyn_imp_staging_worker        │
                  │  full-load from source           │
                  │  → INSERT into staging.<table>   │
                  └──────────────────────────────────┘

                  ┌──────────────────────────────────┐
                  │  *_dyn_imp_scd_control           │
                  │  reads meta, iterates tables     │
                  └────────────────┬─────────────────┘
                                   │ tRunJob per table
                                   ▼
                  ┌──────────────────────────────────┐
                  │  *_dyn_imp_scd_worker_ddl        │
                  │  (idempotent, RunIf-guarded)     │
                  │  creates scd.<table> + view      │
                  └────────────────┬─────────────────┘
                                   ▼
                  ┌──────────────────────────────────┐
                  │  *_dyn_imp_scd_dispatcher        │
                  │  reads new META_BATCH_IDs        │
                  └────────────────┬─────────────────┘
                                   │ tRunJob per batch
                                   ▼
                  ┌──────────────────────────────────┐
                  │  *_dyn_imp_scd_worker_data       │
                  │  Subjob 1 — New/Update sync      │
                  │  Subjob 2 — Deletion detection   │
                  └──────────────────────────────────┘
```

The same framework is typically also used for **denormalized cubes** — those have a separate `*_Cube` builder job that writes into `staging.*` and a `cube_scd_control` that calls the standard SCD dispatcher/worker. There is no special "cube SCD" logic.

## SCD-Worker-Data — the two subjobs

### Subjob 1 — Forward sync (New + Update + Unchanged)

```
tDBInput (staging current batch with inline HASHBYTES) ─┐
                                                        ├─ tMap (HK/HV compare)
tDBInput (scd._current view, only META_HK, META_HV) ────┘            │
                                                                     ├─ "updated"    → tDBOutput (scd.<table>)
                                                                     ├─ "new_data"   → tDBOutput (scd.<table>)
                                                                     └─ REJECT (unchanged, dropped)
```

Decisions in the tMap:
- HK in lookup ∧ HV equal → **REJECT** (unchanged)
- HK in lookup ∧ HV different → **updated** (insert new version with current `META_LOAD_DATETIME`, old version becomes "history")
- HK not in lookup → **new_data** (insert)

Both `updated` and `new_data` are pure INSERTs into the SCD table. There is no UPDATE; the LEAD-window view handles "which row is current".

### Subjob 2 — Deletion detection (Tombstone insert)

```
tDBInput (scd._current view, all columns) ──────┐
                                                ├─ tMap (HK anti-join)
tDBInput (staging current batch, HK + HV) ──────┘            │
                                                             ├─ Matches  → dropped
                                                             └─ Reject (HK not in staging) → tDBOutput (scd.<table>, META_DELETION_DATETIME=NOW)
```

A record in the current view whose HK is no longer present in the latest full-load staging is considered deleted in the source. The tombstone is inserted as a new SCD row with `META_DELETION_DATETIME` set and a fresh `META_LOAD_DATETIME` (overrides the original load datetime on the row, so it becomes the latest).

## The `_current` view — three flavours

This is where projects diverge — and where bugs hide. Three variants seen in the wild:

### Flavour 1 — LEAD-window (canonical)

```sql
CREATE VIEW <schema>.<view> AS
WITH CTE AS (
    SELECT *,
           LEAD(META_LOAD_DATETIME) OVER (
               PARTITION BY META_HK
               ORDER BY META_LOAD_DATETIME
           ) AS META_NEXT_DATE
    FROM <schema>.<table>
)
SELECT *
FROM CTE
WHERE META_NEXT_DATE IS NULL;
```

Exactly one row per `META_HK` — the latest version. Tombstones appear as rows where `META_DELETION_DATETIME` is non-NULL. **This is what the `scd_worker_ddl` job generates.**

### Flavour 2 — LEAD-window + Tombstone-Filter (recommended)

```sql
…
WHERE META_NEXT_DATE IS NULL
  AND META_DELETION_DATETIME IS NULL;
```

Tombstones disappear from the current view entirely. Downstream consumers (DQ checks, reports, cubes) see only live records. **This is the safer default**, because it eliminates the failure mode in Flavour 1 where a downstream job re-reads tombstones unintentionally.

### Flavour 3 — Pass-through (BROKEN)

```sql
CREATE VIEW <schema>.<view> AS
SELECT <columns> FROM <schema>.<table>;
```

All historical versions including tombstones. **Catastrophic when fed back into Subjob 2 of `scd_worker_data`** — see "Common bug" below.

## Common bug: exponential tombstone growth from a pass-through view

If the `_current` view is a pass-through (Flavour 3 above) AND the SCD framework is still being used for deletion detection:

- Subjob 2 reads `_current` and sees all rows for a HK
- HK has e.g. 1 tombstone → view returns 1 row → 1 new tombstone written → table has 2 tombstones for HK
- Next run: 2 rows in view → 2 new tombstones → 4 total
- Run N: 2^N rows for that HK

After 18 weekly runs (~4 months), one HK has 262143 tombstones. A table with many deleted HKs balloons quickly. Symptoms:
- Long-running `*_scd_worker_data` jobs that suddenly start hanging
- Lock-timeouts on the SCD table (transaction held open by the worker while inserting tombstones)
- SCD table size 10–100× the staging size
- DB query: `SELECT META_HK, COUNT(*) FROM <scd_table> WHERE META_DELETION_DATETIME IS NOT NULL GROUP BY META_HK ORDER BY 2 DESC` returns counts that are powers of 2

**How the bug enters the codebase:** `scd_worker_ddl` correctly generates Flavour 1. The pass-through must have been written **manually** in the DB via `CREATE OR ALTER VIEW`, typically by someone trying to "speed up" the view because `LEAD` is slow on large tables without an index.

**Real-world example:** on one project a cube's `_current` view was manually changed to pass-through. ~18 weekly runs later the worst HK had reached 262143 tombstones (2^18 − 1) before it was caught. When you hit such an incident, write it up in the affected project's own `docs/` (Layer 3) — not here.

## Audit checklist for any project using this framework

When you encounter this pattern in a new (or familiar) project, run through:

1. **List all `_current` views and classify their definitions** — query `sys.sql_modules.definition` and check for `LEAD` and `META_NEXT_DATE IS NULL`. Any pass-through is a bug, any LEAD-without-Tombstone-Filter is a latent risk if Subjob 2 reads it.
2. **Verify indexes on SCD tables** — at minimum a clustered index on `(META_HK, META_LOAD_DATETIME)`. Without it, the LEAD-Window does a full table scan + sort on every read. Cube tables in particular hit this hard.
3. **Verify staging-housekeeping is configured** — staging tables that accumulate batches mean the SCD dispatcher loops over many `META_BATCH_ID`s per run; each iteration does one full SCD pass (including deletion detection). High batch counts compound performance issues.
4. **Spot-check `META_BATCH_ID` indexes on staging tables** — the dispatcher's `SELECT DISTINCT META_BATCH_ID FROM staging.X WHERE META_BATCH_ID > N` is a full scan without one. Look at `sys.dm_db_missing_index_details` for evidence.
5. **Check `tDBCommit_1` placement** — the SCD worker writes all inserts in one transaction, committed only at the end of all subjobs. For very large change sets this is a T-Log pressure source. Some projects split this into per-subjob commits.
6. **Watch for "ROWS_BUFFER_SIZE" on tMap_2 in the worker** — default `2000000` means Disk-Spill once the deletion-detection main flow exceeds 2M rows. On large SCD tables this is the silent slowdown.

## Variant: HK/HV column registration

The framework reads the columns to include in `META_HK` and `META_HV` from meta-table fields like `columns_business_keys` and (the difference of) `columns_to_import`. These are comma-separated lists. **Check the project's specific spelling** — some use `columns_hash_key` / `columns_hash_value`, others split keys per business-domain.

Risk to flag during review:
- **MD5 over `concat(col1, col2, ...)` without a delimiter**: combinations like `('AB','C')` vs. `('A','BC')` hash identically. Low-probability collisions, but unaudited. The cleaner pattern is `concat(col1, '|', col2, '|', ...)` or `HASHBYTES('MD5', concat_ws('|', ...))`.

## Variant: separate worker_ddl runs

`scd_worker_ddl` typically wraps its CREATE VIEW / SELECT INTO statements in a `RunIf` condition that checks `INFORMATION_SCHEMA.VIEWS` for the existence of the `_current` view. So the DDL runs **once per new table**, not on every job run. This means: if the meta-table later changes which columns are part of HK/HV, the existing view will NOT be regenerated. Watch for stale view DDL after meta-table edits.
